# Core 1.4.0

## Resumen

Esta versión actualiza el runtime base del template a **Java 25** y **Spring Boot 4.1.1** (Spring Framework 7 / Jakarta EE 11), migra todo el uso de Jackson embebido en el Core a **Jackson 3** (`tools.jackson.*`, la librería JSON que trae Spring Boot 4 por defecto), y ajusta las clases que Spring Boot 4 modularizó fuera de `spring-boot-autoconfigure`. Validado compilando (`mvn compile`, `mvn test-compile`) y empaquetando (`mvn package`) el proyecto completo.

**Motivación:** mantener el template sobre versiones soportadas de Java y Spring Boot.

---

## Reglas de trabajo del proyecto reorganizadas (no es cambio del Core)

**Archivos** (reglas de trabajo del proyecto, no forman parte del Core compartido):

- `AGENT.md` y `convenciones-backend.md` se reemplazan por `AGENTS.md` (índice) + `docs/rules/*.md` (un archivo por tema: `git.md`, `versionado.md`, `idioma-y-estilo.md`, `entidades-y-dtos.md`, `controllers-y-endpoints.md`, `base-de-datos.md`, `integraciones-y-entorno.md`, `testing.md`, `documentacion.md`), evitando mezclar reglas de negocio distintas en un mismo archivo.
- `CLAUDE.md` — nuevo, importa `AGENTS.md` para que Claude Code cargue automáticamente todas las reglas de `docs/rules/` al iniciar sesión en este proyecto.
- La metodología de DTOs específicos por caso de uso (`GET/POST /api/{controller}/{uuid}/{caso-de-uso}` y `POST /api/{controller}/{caso-de-uso}` para altas reducidas) vive en `docs/rules/controllers-y-endpoints.md` (regla de decisión y rutas) y `docs/rules/entidades-y-dtos.md` (convención de nombres `{Entidad}{CasoDeUso}RequestDTO`/`ResponseDTO`).

**Motivación:** `GET /uuid/{uuid}` y `POST /save` heredados usan un único DTO con todos los campos de la entidad; en entidades grandes esto transporta más datos de los que el front necesita. `core.md` sigue documentando únicamente los 4 endpoints que el Core provee de forma automática; las reglas de metodología de trabajo (cuándo usarlos vs. crear un DTO por caso de uso) viven en `docs/rules/`, no en `Core/Docs`.

## Jackson 2 → Jackson 3

**`Core/Security/JacksonConfig.java`:**

- Antes: `new ObjectMapper()` + `registerModule(new JavaTimeModule())` + `setTimeZone(...)` + `disable(...)` mutando la instancia.
- Después: `JsonMapper.builder().defaultTimeZone(...).disable(DateTimeFeature.WRITE_DATES_AS_TIMESTAMPS).disable(SerializationFeature.FAIL_ON_EMPTY_BEANS).build()`. `JavaTimeModule` ya no se registra: en Jackson 3 el soporte de `java.time` (JSR-310) está incluido de forma nativa en `jackson-databind`. `WRITE_DATES_AS_TIMESTAMPS` se movió de `SerializationFeature` a `DateTimeFeature` (paquete `tools.jackson.databind.cfg`).

**`Core/Configuration/LogDataSanitizer.java`:**

- `JsonNode.fields()` (devolvía `Iterator<Map.Entry<String,JsonNode>>`) fue removido en Jackson 3. Se reemplazó por `node.properties()` (devuelve `Set<Map.Entry<String,JsonNode>>`) iterado con for-each; se quitó el import `java.util.Iterator`, que quedó sin uso.

**`Core/Service/CrypterService.java` y `Core/Entity/DTO/ImagenCrypterDTO.java`:**

- `JsonProcessingException` (checked, extendía `IOException`) fue removido en Jackson 3: la excepción base ahora es `tools.jackson.core.JacksonException`, que es **unchecked** (extiende `RuntimeException`). Se reemplazó el tipo importado y capturado en los `catch`.

**Paquetes migrados de `com.fasterxml.jackson.{core,databind}.*` a `tools.jackson.{core,databind}.*`** (solo `ObjectMapper`, `JsonNode`, `ArrayNode`, `ObjectNode`, `JsonNodeFactory`, `TypeReference`, `JacksonException`; las anotaciones `@JsonFormat`/`@JsonInclude`/`@JsonIgnore` no cambiaron de paquete: `jackson-annotations` sigue siendo `com.fasterxml.jackson.annotation.*` en Jackson 3):

- `Core/Configuration/LogDataSanitizer.java`
- `Core/Service/CrypterService.java`
- `Core/Entity/DTO/ImagenCrypterDTO.java`
- `Core/Repository/Impl/RepositoryImpl.java`
- Tests: `Core/Configuration/LogDataSanitizerTest.java`, `Core/Configuration/TrazabilidadAspectTest.java`, `SecurityIntegrationIT.java`

**`pom.xml`:**

- Se elimina la dependencia `com.fasterxml.jackson.datatype:jackson-datatype-jsr310`: Spring Boot 4 ya no gestiona su versión (el BOM pasó a Jackson 3) y quedó redundante, ya que `tools.jackson.databind` trae JSR-310 incluido de forma nativa.

## Clases movidas por la modularización de Spring Boot 4

Spring Boot 4 sacó varias clases de `spring-boot-autoconfigure`/`spring-boot-test-autoconfigure` a módulos dedicados:

- `Application.java`: `EntityScan` → `org.springframework.boot.persistence.autoconfigure.EntityScan` (antes `org.springframework.boot.autoconfigure.domain`).
- `Core/Service/CaptchaService.java`: `RestTemplateBuilder` → `org.springframework.boot.restclient.RestTemplateBuilder` (antes `org.springframework.boot.web.client`). `spring-boot-starter-web` ya no trae `RestTemplateBuilder` de forma transitiva; se agregó `spring-boot-starter-restclient` al `pom.xml`.
- `SecurityIntegrationIT.java`: `@AutoConfigureMockMvc` → `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` (antes `org.springframework.boot.test.autoconfigure.web.servlet`); se agregó `spring-boot-starter-webmvc-test` (scope `test`) al `pom.xml`, ya que ese soporte salió de `spring-boot-starter-test`.
- `SecurityIntegrationIT.java`: `@MockBean` (removido en Boot 4, deprecado desde 3.4) → `@MockitoBean` de `org.springframework.test.context.bean.override.mockito.MockitoBean`.
- `Core/Configuration/RequestLoggingFilter.java`: el constructor de un solo argumento `new ContentCachingRequestWrapper(request)` fue removido; ahora requiere `contentCacheLimit` explícito. Se agregó la constante `REQUEST_CACHE_LIMIT = 100_000` (bytes) y se usa `new ContentCachingRequestWrapper(request, REQUEST_CACHE_LIMIT)`.

**`pom.xml` — rename de starter:**

- `spring-boot-starter-aop` → `spring-boot-starter-aspectj` (Spring Boot 4 renombró el starter; el artefacto viejo no tiene versión gestionada en el BOM 4.1.1 y rompe la build). El proyecto usa `@Aspect`/`@Pointcut`/`@Around` (anotaciones de `org.aspectj.lang.annotation`) en `TrazabilidadAspect`, por lo que sigue siendo necesario.

## Java 25 y Spring Boot 4.1.1

**`pom.xml`:**

- `spring-boot-starter-parent`: `3.2.4` → `4.1.1`.
- `java.version`: `17` → `25`.
- `maven-compiler-plugin`: `3.11.0` → `3.15.0` (soporte de `--release 25`).
- `maven-surefire-plugin` / `maven-failsafe-plugin`: `3.2.5` → `3.6.0`.
- `net.bytebuddy:byte-buddy` / `byte-buddy-agent`: `1.16.1` → `1.18.12` (las versiones previas no reconocen el bytecode de Java 25 — requerido por Mockito en los tests).

**No requirió cambios** (siguen compatibles sin tocar código):

- `Core/Security/SecurityConfig.java`: ya usa `SecurityFilterChain` + `NimbusJwtDecoder(JWTProcessor)` de bajo nivel, API que sigue vigente en Spring Security 7.
- `org.projectlombok:lombok:1.18.44`: ya soporta Java 25 (el soporte se agregó en 1.18.40).

**Pendiente de verificación real con JDK 25** (este release se validó compilando/empaquetando con `--release 24` por no haber JDK 25 disponible en la máquina de desarrollo; los `Dockerfile` de build sí usan `maven:3.9-eclipse-temurin-25`):

- Correr la build completa (`mvn verify`, que incluye los tests `*IT.java` con `maven-failsafe-plugin`) con un JDK 25 real antes de dar por cerrada la migración en un entorno con esa versión instalada.

**Nota — fallas de tests preexistentes, no relacionadas con esta migración:**

Al migrar se detectaron 18 tests que ya fallaban en Core 1.3.0 / Java 17 / Boot 3.2.4 (`AuthServiceTest`, `UserControllerTest`, `BaseUserServiceSecurityTest`), todos con `NullPointerException` en `userCompanyRoleRepository` o aserciones de excepción esperada que no se lanza. Se confirmó haciendo `git stash` de este cambio y corriendo `mvn test` sobre el código anterior: la lista de fallas es idéntica. No son parte de esta migración.

## Migración desde Core 1.3.0

1. Instalar JDK 25 en el entorno de desarrollo y en cualquier imagen Docker/CI que compile el proyecto (los `Dockerfile` de `deploy/plantillas/spring-3.9-java-25-*` ya usan `maven:3.9-eclipse-temurin-25` / `eclipse-temurin:25-jre-jammy`).
2. Reemplazar `spring-boot-starter-aop` por `spring-boot-starter-aspectj` en el `pom.xml` si el proyecto lo declaraba explícitamente.
3. Agregar `spring-boot-starter-restclient` si el proyecto usa `RestTemplateBuilder`/`RestTemplate` autoconfigurado, y `spring-boot-starter-webmvc-test` (scope test) si usa `@AutoConfigureMockMvc`/`MockMvc`.
4. Migrar imports de clases movidas por Boot 4: `EntityScan` (→ `org.springframework.boot.persistence.autoconfigure`), `RestTemplateBuilder` (→ `org.springframework.boot.restclient`), `@AutoConfigureMockMvc` (→ `org.springframework.boot.webmvc.test.autoconfigure`).
5. Reemplazar `@MockBean`/`@SpyBean` por `@MockitoBean`/`@MockitoSpyBean` (`org.springframework.test.context.bean.override.mockito`).
6. Si el proyecto usa `new ContentCachingRequestWrapper(request)` (un solo argumento), pasar a la variante con `contentCacheLimit` explícito.
7. Migrar imports propios de `com.fasterxml.jackson.databind.*`/`com.fasterxml.jackson.core.*` a `tools.jackson.databind.*`/`tools.jackson.core.*` (las anotaciones `com.fasterxml.jackson.annotation.*` no cambian). Puntos comunes: `ObjectMapper` (inmutable, construir con `JsonMapper.builder()...build()` si se necesita configurar), `JsonNode.fields()` → `JsonNode.properties()`, `JsonProcessingException` → `JacksonException` (ahora unchecked).
8. Revisar dependencias que sigan expuestas en Jackson 2 (por ejemplo librerías de terceros como `jjwt-jackson`): conviven sin conflicto con Jackson 3 porque usan paquetes distintos (`com.fasterxml.jackson.*` vs `tools.jackson.*`), no requieren cambios salvo que el propio proyecto quiera migrarlas.
9. Si el proyecto define `spring.security.oauth2.resourceserver.jwt.jwk-set-uri` (autoconfiguración de Spring Boot, no el bean manual del Core), revisar el comportamiento de `JwkSetUriJwtDecoderBuilderCustomizer` y los timeouts por defecto de Spring Security 7 antes de desplegar a producción.
