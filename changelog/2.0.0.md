# Core 2.0.0

## Resumen

Esta versión parte el Core en **12 módulos Maven independientes** y elimina la dependencia del Core hacia el código del proyecto. Hasta 1.4.0 el Core era una carpeta única, obligatoria y no editable, que además importaba `com.blue.open.Code.User.User`, `com.blue.open.Code.Company.Company` y `com.blue.open.Code.Configuration.ConfiguracionService` por nombre concreto: todo proyecto estaba obligado a tener esas clases, esas tablas y ese modelo multi-empresa, usara o no cada cosa.

A partir de 2.0.0 un proyecto declara solo los módulos que necesita, y el Core se adapta a través de puertos en vez de imponer una estructura.

**Problema que resolvía:** proyectos que no encajaban en la estructura del Core no tenían salida. Sobraban tablas (empresas, tokens de acceso, refresh tokens), sobraban endpoints (los 4 heredados en entidades grandes), y no se podía hacer borrado físico. La única alternativa era parchear el Core, que es justamente lo que `modificaciones-del-core.md` intentaba administrar.

**Validado con** `mvn verify` (19 tests unitarios + el test de integración que levanta el contexto completo sobre H2).

## Módulos

| Módulo | Contiene | Tablas propias |
|---|---|---|
| `core-kernel` | Paginado, entidades base, mappers, excepciones, fechas GMT-3, Jackson, trazabilidad, header `API-Version`, smoke tests y **los puertos** | — |
| `core-crud` | `AbstractController` / `AbstractService` y los 4 endpoints heredados | — |
| `core-identity` | Usuario, rol, permiso, login por password, recuperación de contraseña | `auth_users`, `auth_roles`, `auth_permissions`, `auth_roles_permissions`, `security_code` |
| `core-monoempresa` | Scoping simple: usuario → rol directo | `auth_user_roles` |
| `core-multiempresa` | Scoping por empresa, header `X-Company-Uuid`, registro público con alta de empresa | `companies`, `auth_users_companies`, `auth_user_company_roles` |
| `core-protocolo-jwt` | Login JWT y refresh tokens | `auth_jwt_refresh_tokens` |
| `core-protocolo-apikey` | Tokens de acceso personales | `auth_user_access_tokens` |
| `core-protocolo-sso` | SSO externo y Malvinas | — |
| `core-mail` | Envío de emails | — |
| `core-crypter` | Archivos encriptados | — |
| `core-sm3` | Archivos públicos | — |
| `core-captcha` | Verificación de hCaptcha | — |

`core-monoempresa` y `core-multiempresa` son **excluyentes**: un proyecto declara uno de los dos, o ninguno (usuarios sin roles).

El reactor queda como `pom.xml` (padre, versión del Core) + `core/core-*` + `app` (el proyecto, con versión propia).

## Puertos: el Core ya no importa `Code`

`grep -rn "com.blue.open.Code" core --include=*.java` devuelve **cero imports** (solo quedan menciones en comentarios que explican la deuda anterior).

| Puerto | Reemplaza | Implementación por defecto |
|---|---|---|
| `Kernel.Puertos.ProveedorDeUsuarioActual` | `(User) authService.getActualOrNull()` dentro de `AbstractService` | `UsuarioActualAnonimo` (auditoría en null, endpoints con permisos en 403). `core-identity` lo implementa con `AuthService` |
| `Kernel.Puertos.ProveedorDeConfiguracion` | `ConfiguracionService` importado desde el Core | `ConfiguracionDesdePropiedades` (lee del `application.properties`) |
| `Kernel.Puertos.ProveedorDeVersion` | `com.blue.open.Version` importado desde el Core | Lee `app.version`; el proyecto publica un bean con su `Version.VERSION` |
| `Kernel.Puertos.EnviadorDeMail` | `JavaMailSender` como clase concreta obligatoria | Sin `core-mail` no hay bean y el error explica que falta el módulo |
| `Kernel.Puertos.IntegracionExterna` | La lista fija de integraciones dentro del smoke test | El smoke test recorre los beans presentes; agregar o quitar una integración no lo toca |
| `Crud.Guardia.GuardiaDeEndpoint` | `authService.valid(List.of(SYSADMIN))` fijo en `AbstractController` | `GuardiaDenegarTodo`; con `core-identity`, `GuardiaSysadmin` (comportamiento de 1.x) |
| `Crud.Borrado.EstrategiaDeBorrado` | El borrado lógico hardcodeado | `BorradoLogico` / `BorradoFisico` según la entidad |
| `Identity.Puertos.ResolutorDePermisos` | Las queries a `auth_users_companies` dentro de `AuthService` | Sin scoping devuelve vacío; lo implementan `core-monoempresa` y `core-multiempresa` |
| `Identity.Puertos.ValidadorDeContexto` | La validación de empresa dentro de `AuthService.valid()` | No-op; `core-multiempresa` exige pertenencia a la empresa del header |
| `Identity.Puertos.EstrategiaDeAutenticacion` | Los 5 servicios de auth inyectados por nombre en `AuthService` | Cada `core-protocolo-*` registra el suyo; `auth.protocols` elige entre los presentes |
| `Identity.Puertos.CatalogoDeAutorizacion` | `Class.forName("com.blue.open.Code.Auth.PermissionEnum")` | Catálogo vacío; el proyecto publica un bean con sus enums |
| `Identity.Puertos.InicializadorDeAutorizacion` | La creación de las empresas "Sistema" y "BlueOpenData" en el inicializador | No-op; lo implementan los módulos de scoping |
| `Identity.Puertos.SincronizadorDeRolesExternos` | La escritura directa de `UserCompanyRole` desde SSO/Malvinas | No-op; `core-multiempresa` lo implementa |
| `Identity.Repository.UsuarioRepositorio` | `UserRepository extends EntityRepository<User>` en el Core | `UsuarioRepositorioJpa` descubre la entidad de usuario del proyecto en el metamodelo de JPA |
| `Multiempresa.Repository.EmpresaRepositorio` | `BaseCompanyRepository extends EntityRepository<Company>` | `EmpresaRepositorioJpa`, mismo mecanismo |
| `Multiempresa.Service.AltaDeEmpresa` | El alta de empresa dentro de `BaseUserService.publicRegister` | Delega en el mapper de empresa del proyecto |

## Flexibilidad nueva

### Endpoints heredados opt-in por entidad

```java
@RestController
@RequestMapping("/api/producto")
@EndpointsHeredados({ OperacionHeredada.UUID, OperacionHeredada.PAGINATE })
public class ProductoController extends AbstractController<...> { }
```

Sin la anotación se publican los cuatro, como en 1.x. Los endpoints no declarados no se registran en el `RequestMapping`: responden **404, no 403**. Lo resuelve `EndpointsHeredadosHandlerMapping`, registrado vía `WebMvcRegistrations`.

Un proyecto grande también puede no depender de `core-crud` y quedarse solo con el kernel: conserva el paginado, las excepciones y la trazabilidad sin heredar ningún endpoint.

### Borrado físico

`AbstractEntity` se partió en dos:

- `AbstractEntity`: id, uuid, fechas y auditoría de creación/edición.
- `EntidadConBorradoLogico extends AbstractEntity`: agrega `status`, `date_deleted` e `id_user_deleted`, y la validación de transiciones de `status`.

Una entidad que **no** extiende `EntidadConBorradoLogico` no tiene columna `status`, el `DELETE` borra la fila y el paginado no le agrega ningún filtro de vigencia. La estrategia se resuelve sola por el tipo de la entidad (`SelectorDeBorrado`); un proyecto puede registrar la suya con un `@Order` menor.

Consecuencia: los finders que filtran por `status = 0` se movieron de `EntityRepository` a `EntityRepositoryBorradoLogico`. Un repositorio de una entidad con borrado lógico debe extender el segundo.

### Multiempresa opcional

`core-identity` no sabe qué es una empresa. El header `X-Company-Uuid`, `getCurrentCompanyOrThrow()`, el filtro del paginado por empresa y el registro público con alta de empresa viven todos en `core-multiempresa`.

El id de la empresa de sistema dejó de estar hardcodeado como `1` dentro de las consultas JPQL: ahora se resuelve por `core.multi-company.system-uuid`.

### Protocolos de autenticación opcionales

Cada `core-protocolo-*` registra una `EstrategiaDeAutenticacion` y trae su propio changelog de Liquibase. Un proyecto que no usa tokens personales no declara `core-protocolo-apikey`, no crea `auth_user_access_tokens` y no publica `/user/create-token`.

`SecurityConfig` se partió: la cadena de seguridad web y el CORS quedaron en `core-identity` (`SeguridadWebConfig`, `@ConditionalOnMissingBean`), y el `JwtDecoder` de Malvinas pasó a `core-protocolo-sso` con `@ConditionalOnProperty(auth.malvinas.url)`. **Esto arregla un bug de 1.x**: el bean del decoder se construía siempre y cualquier proyecto sin esa propiedad arrancaba con una URL nula.

### Un repositorio base para todos

`EntityRepositoryBase` (registrado con `repositoryBaseClass` en `@EnableJpaRepositories`) implementa `paginate()` para cualquier repositorio. Desaparecen los `{Entidad}RepositoryCustom` + `{Entidad}RepositoryImpl` que existían solo para exponer el paginado: se borraron 12 archivos y las entidades nuevas ya no los necesitan.

## Versionado

- La versión del Core es la del artefacto Maven (`core-parent`, propiedad `core.version`). `CoreVersion.CORE_VERSION` como `String` escrito a mano **ya no existe**: `CoreVersion.get()` lee `core-version.properties`, que Maven completa en el build, así que no puede quedar desincronizada.
- El proyecto (`app`) tiene su propia versión en su `pom.xml` y en `Version.java`.
- `/info` expone `version` (del proyecto) y `coreVersion` (del artefacto).
- **`modificaciones-del-core.md` se elimina.** Con el Core como dependencia versionada ya no se parchea: si algo no entra por configuración, hook o puerto, es un issue del Core y sale en la versión siguiente.

## Base de datos

El schema monolítico (`2026-07-06-create-initial-schema.yaml`, 11 tablas) se partió: cada módulo trae su changelog dentro del jar y el proyecto incluye solo los que usa.

```yaml
# app/src/main/resources/db/changelog/db.changelog-master.yaml
databaseChangeLog:
  - include: { file: db/changelog/core-identity.yaml }
  - include: { file: db/changelog/core-multiempresa.yaml }
  - include: { file: db/changelog/core-protocolo-jwt.yaml }
  - include: { file: db/changelog/core-protocolo-apikey.yaml }
  - include: { file: changes/2026-07-06-create-app-schema.yaml, relativeToChangelogFile: true }
  - include: { file: changes/2026-07-06-insert-required-data.yaml, relativeToChangelogFile: true }
```

Regla nueva: **ningún módulo toca tablas de otro**. La FK `auth_roles.company_id → companies` la agrega `core-multiempresa` por changeset propio (la columna la crea `core-identity` sin FK), y la columna `cuit` de `companies` la agrega el proyecto, porque es suya y no del Core.

### Cambios de columnas

Las tablas y columnas son las mismas de 1.4.0. Lo que cambió es cómo las mapea el Core: `SecurityCode`, `UserCompanyRole`, `UserAccessToken` y `JwtRefreshToken` referencian al usuario y a la empresa **por id** (`user_id`, `company_id` como `Long`) en vez de por asociación JPA, y `Role.company` pasó a `Role.idCompany`. Es lo que permite que el Core no nombre las entidades concretas del proyecto. El schema SQL no se modifica.

## Bugs arreglados de paso

- **`ExecutionTraceAspect` entraba en recursión infinita** al resolver la clave `DEBUG`: el proveedor de configuración pasa por un `*Service` del proyecto, que vuelve a entrar en el mismo aspecto. Terminaba en `StackOverflowError` al levantar el contexto. Se agregó el mismo guard `ThreadLocal` que ya tenía `RequestLoggingFilter`.
- **`JwtDecoder` de Malvinas obligatorio** (ver arriba).
- **`PaginateList` sin `entityClass`**: `EntityRepositoryBase` ahora lo completa con el `domainClass` del repositorio si viene en null.

## Migración desde Core 1.4.0

Un proyecto existente puede quedarse en 1.4.0 (es la copia embebida que ya tiene). Para migrar:

1. **Estructura del repo**: mover el proyecto a `app/` y agregar el `pom.xml` padre con los módulos del Core. El jar pasa a generarse en `app/target/`, no en `target/` — revisar el `Dockerfile` de `deploy/`.
2. **Declarar módulos**: en `app/pom.xml`, solo los que el proyecto usa. Si no usa empresas, `core-monoempresa` en lugar de `core-multiempresa`.
3. **Imports**: aplicar la tabla de renombre de paquetes.
4. **Entidades**: las que tengan borrado lógico pasan de `extends AbstractEntity` a `extends EntidadConBorradoLogico`; sus repositorios, de `EntityRepository` a `EntityRepositoryBorradoLogico`.
5. **Usuario y empresa**: `User extends BaseUser`, `Company extends BaseCompany`. El proyecto declara sus propios `UserRepository` y `CompanyRepository` (el Core ya no los trae).
6. **Roles y permisos**: publicar un bean `CatalogoDeAutorizacion` con los enums del proyecto (ya no se descubren por reflexión).
7. **Versión**: publicar un bean `ProveedorDeVersion` en `Application` que devuelva `Version.VERSION`.
8. **Configuración dinámica**: si el proyecto tiene tabla `configurations`, publicar un `ProveedorDeConfiguracion` `@Primary` que la lea (ver `Code/Configuration/ConfiguracionDesdeBase.java`).
9. **`@EnableJpaRepositories` / `@EntityScan`**: apuntar a `com.blue.open.Code` y `com.blue.open.Core`, y agregar `repositoryBaseClass = EntityRepositoryBase.class`.
10. **Liquibase**: reemplazar el schema monolítico por los includes de los módulos usados; mover al changelog del proyecto las columnas propias (como `cuit`).
11. **Borrar** `{Entidad}RepositoryCustom` y `{Entidad}RepositoryImpl`: `EntityRepositoryBase` ya provee `paginate()`.
12. **Controllers de usuario/rol/empresa**: el Core ya no publica `RoleController` ni los endpoints de login JWT y tokens dentro de `BaseUserController`. El proyecto declara `RoleController extends BaseRoleController<RoleService>`; los endpoints de JWT y de tokens los publican sus propios módulos.
