# Core 3.3.1

## Resumen

El CORS por defecto de `core-identity` expone los encabezados `Content-Disposition`, `X-Trace-Id` y `API-Version`
(`Access-Control-Expose-Headers`). Es un arreglo compatible: no cambia ningún endpoint, DTO ni permiso.

## Cambios

### CORS (`core-identity`)

`SeguridadWebConfig.corsConfigurationSource()` agrega `setExposedHeaders(...)` con:

| Encabezado | Para qué lo lee el front |
|---|---|
| `Content-Disposition` | Nombre del archivo de las descargas (blob) |
| `X-Trace-Id` | Mostrar el `traceId` para soporte aunque el cuerpo de la respuesta no sea JSON |
| `API-Version` | Registrar contra qué versión del backend está hablando |

Hasta 3.3.0 el backend ya mandaba esos encabezados, pero el navegador los ocultaba al JavaScript de un front servido
desde otro origen que la API (por ejemplo, en desarrollo: front en `https://localhost:4201` y API en
`http://localhost:7008`), y `respuesta.headers.get('Content-Disposition')` devolvía `null`. Con el front y la API en
el mismo origen (detrás de nginx en `/api`) no había problema.

## Qué tiene que hacer un proyecto

Nada, salvo que publique su propio `CorsConfigurationSource`: en ese caso, si necesita leer esos encabezados desde
otro origen, agrega el mismo `setExposedHeaders(...)` en su bean.
