# Core 2.4.0

## Resumen

Todo error de la API pasa a llevar un código estable (`codigo`), además del `userMessage` de texto libre
que ya existía. Hoy el front solo puede discriminar un error por el status HTTP o comparando el texto de
`userMessage`, que no es un contrato: cambiar una palabra rompe en silencio a quien lo compara. Con
`codigo`, el texto queda libre para reformularse y el front discrimina por un identificador estable.

El diseño completo (motivación, decisiones, ejemplos) está en
[`docs/arquitectura/errores/README.md`](https://github.com/SM-SOLUCIONES/sm-template/blob/main/backend-v2/docs/arquitectura/errores/README.md); la regla de
cumplimiento obligatorio quedó en [`docs/rules/errores.md`](https://github.com/SM-SOLUCIONES/sm-template/blob/main/backend-v2/docs/rules/errores.md) (nueva, enlazada
desde `AGENTS.md`).

De paso, se cerraron varias fugas de datos internos que tenía el formato de error anterior: el body ya no
expone `stackTrace`, `cause` ni el resto de los campos que Jackson sacaba de `Throwable`, y
`developerMessage` (el detalle técnico) dejó de viajar en la respuesta HTTP: ahora es un campo interno de
`CustomException` que solo se loguea.

## Estado de la migración

Esta versión migra **`core-kernel`** completo (interfaz, handler y sus propios 25 `throw`). Los demás
módulos del Core (`core-crud`, `core-identity`, `core-multiempresa`, los `core-protocolo-*`,
`core-crypter`, `core-sm3`, `core-mail`, `core-captcha`) y `app` todavía usan los constructores de
`CustomException` que esta versión elimina: **el reactor completo no compila** hasta que cada uno se
migre en un commit propio. Mientras tanto, `core-kernel` se compila y se prueba de forma aislada con
`mvn -pl core/core-kernel -am`.

## Cambios

- **`core-kernel`**:
  - `CodigoDeError` (interfaz nueva): la implementa un enum por módulo del Core y uno por proyecto.
    Expone `codigo()` (el identificador estable), `status()` y `mensajePorDefecto()`.
  - `CodigoDeErrorKernel` (enum nuevo): los códigos propios de este módulo (paginado, borrado lógico,
    permisos, y las respuestas genéricas del handler).
  - `CustomException`: los 7 constructores anteriores (mensajes libres, con o sin `HttpStatus`) se
    eliminan. Los 4 nuevos reciben siempre un `CodigoDeError`. Suma el método encadenable
    `conDato(clave, valor)` para el campo `datos`, que descarta solo (con un `warn` en el log) cualquier
    clave que matchee el criterio de `LogDataSanitizer`.
  - `ErrorResponseDTO` (nuevo): es el único objeto que se serializa como body de una respuesta de error.
    A diferencia de `CustomException`, nunca expone `developerMessage` ni `cause`.
  - `SubError` pierde el campo `value` (podía filtrar el valor rechazado de un campo sensible, como una
    contraseña, en un error de validación).
  - `CustomRestExceptionHandler`: arma la respuesta con `ErrorResponseDTO`. Suma dos overrides que antes
    no existían (`handleHttpRequestMethodNotSupported`, `handleHttpMediaTypeNotSupported`), así que ya no
    hay ninguna excepción que llegue a un controller y se escape al formato de `CustomException`.
    `handleMethodArgumentNotValid` completa `errores` con un `SubError` por campo en vez de volcar un
    `Map.toString()` en `developerMessage`.

## Migración

Migrar un `throw new CustomException(...)` existente es mecánico:

```java
// Antes
throw new CustomException("No existe el registro");
throw new CustomException(HttpStatus.FORBIDDEN, "No tenes permiso", "detalle tecnico");

// Ahora: se define (o reutiliza) un codigo en el enum del modulo/proyecto que corresponda
throw new CustomException(CodigoDeErrorCrud.REGISTRO_NO_ENCONTRADO);
throw new CustomException(CodigoDeErrorKernel.SIN_PERMISO, "detalle tecnico");
```

1. Buscar si la situación ya tiene un código en el enum del módulo o del proyecto (regla 5 de
   [`docs/rules/errores.md`](https://github.com/SM-SOLUCIONES/sm-template/blob/main/backend-v2/docs/rules/errores.md)). Si no existe, agregarlo.
2. Si el `userMessage` que se pasaba coincide con el `mensajePorDefecto()` del código, no hace falta
   repetirlo: alcanza `new CustomException(codigo)`.
3. Si el `userMessage` es específico de ese `throw`, usar
   `new CustomException(codigo, userMessage, developerMessage)`.
4. `developerMessage` ya no viaja en la respuesta: se puede pasar con más detalle técnico que antes,
   siempre sin secretos.
5. Un dato que el cliente necesita para resolver el error (no solo para mostrarlo) va en
   `.conDato(clave, valor)`, no concatenado en `userMessage` ni en `developerMessage`.

**Tests con Mockito/Bruno**: un test que asertaba `userMessage` puede seguir asertándolo, pero el
contrato pasa a ser `codigo`: sumar `expect(res.body.codigo).to.equal("...")` en Bruno, o
`assertEquals(CodigoDeErrorX.X, excepcion.getCodigo())` en un test unitario.
