# Core 2.3.0

## Resumen

Todo buscador de la base que devuelve 0 o 1 registro pasa a devolver `Optional<T>` en vez de `T` nullable. Antes, los dos métodos más usados del Core (`findFirstByUuid` y `findFirstByUuidWithStatusIsActive`) devolvían `null` y dejaban el chequeo a cargo del llamador; ahora el compilador obliga a resolver el caso "no existe".

El cambio no se queda en los repositorios: alcanza también al puerto `EstrategiaDeBorrado`, a los puertos `UsuarioRepositorio` / `EmpresaRepositorio` y a los tres hooks de búsqueda de `AbstractService`. Si alguno de ellos hubiera quedado devolviendo `T` nullable, el `null` volvía a entrar por debajo y la regla nacía incumplida dentro del propio Core.

La regla queda escrita en [`docs/rules/consultas.md`](https://github.com/SM-SOLUCIONES/sm-template/blob/main/backend-v2/docs/rules/consultas.md) → "Ausencia de resultado: `Optional`".

## Cambios

- **`core-kernel`**: `EntityRepository.findFirstByUuid` / `findFirstById` y `EntityRepositoryBorradoLogico.findFirstByUuidWithStatusIsActive` / `findFirstByIdWithStatusIsActive` devuelven `Optional<T>`.
- **`core-crud`**: el puerto `EstrategiaDeBorrado.buscarVigentePorUuid` devuelve `Optional<T>`, igual que sus dos implementaciones (`BorradoLogico`, `BorradoFisico`). Los hooks `hookUuidFindDatabase`, `hookSaveGetExistRegister` y `hookDeleteFindByUuid` de `AbstractService` devuelven `Optional<T>`; `getByUuid`, `saveOrCreate` y `delete` los consumen con `orElseThrow` / `orElseGet`. Los mensajes de error de los endpoints heredados no cambian.
- **`core-identity`**: el puerto `UsuarioRepositorio` devuelve `Optional<BaseUser>` en sus siete buscadores (`porUuid`, `porId`, `porUsernameActivo`, `porEmailActivo`, `porEmailNoBorrado`, `porSsoUuidActivo`, `porMalvinasLegajoActivo`). `guardar` y `nuevo` no cambian. Los buscadores de `RoleRepository`, `PermissionRepository` y `SecurityCodeRepository` que devuelven un registro también pasan a `Optional`.
- **`core-multiempresa`**: el puerto `EmpresaRepositorio` devuelve `Optional<BaseCompany>` en `porUuid`, `porUuidActiva`, `porId` y `porNombreActiva`. `UserCompanyRoleRepository.findByUserAndCompany` y `ContextoDeEmpresa.getEmpresaPorDefecto()` también.
- **`core-protocolo-apikey`**: `UserAccessTokenRepository.findFirstByCode` y `findFirstByNameAndIdUserAndStatus` devuelven `Optional`.
- **Sin cambio**: los métodos que devuelven una colección siguen devolviendo `List` (vacía, nunca `Optional<List>`), los `exists...` siguen devolviendo `boolean` y el paginado sigue devolviendo `Page`.
- **Sin cambio**: `EstrategiaDeAutenticacion.getUser()` sigue devolviendo `BaseUser` nullable. Ahí el `null` no significa "no existe el registro" sino "esta request no usa este protocolo", y no es una consulta a la base. Los tres protocolos (`AuthJwtService`, `AuthBasicService`, `AuthTokenService`) mantienen ese contrato.
- **Sin helpers**: no se agregó ningún `findFirstByUuidOrFail`. Cada caso de uso escribe su propio `orElseThrow` con el mensaje que corresponda.

## Migración

Un proyecto que use el Core tiene que recorrer sus llamadas a repositorios y puertos. El compilador las marca todas: no hay forma de que una quede sin migrar en silencio.

La traducción es mecánica y sigue tres formas:

```java
// 1. El registro tiene que existir
// Antes
Producto model = repository.findFirstByUuidWithStatusIsActive(uuid);
if (model == null)
    throw new CustomException("No existe el registro");
// Ahora
Producto model = repository.findFirstByUuidWithStatusIsActive(uuid)
        .orElseThrow(() -> new CustomException("No existe el registro"));

// 2. Si no existe, se crea
// Antes
Configuration c = repository.findFirstByNameAndStatus(key, 0);
if (c == null)
    c = new Configuration(key, defaultValue, true);
// Ahora
Configuration c = repository.findFirstByNameAndStatus(key, 0)
        .orElseGet(() -> new Configuration(key, defaultValue, true));

// 3. Solo interesa si existe
// Antes
User existente = userRepository.findFirstByEmailAndStatusNot(email, -1);
if (existente != null)
    throw new CustomException("Email ya registrado");
// Ahora
if (userRepository.findFirstByEmailAndStatusNot(email, -1).isPresent())
    throw new CustomException("Email ya registrado");
```

- **Repositorios propios del proyecto**: hay que cambiar a mano la firma de cada buscador de 0-o-1 (`{Entidad} findFirstByX(...)` → `Optional<{Entidad}> findFirstByX(...)`). Spring Data soporta `Optional` de forma nativa, tanto en consultas derivadas del nombre como en `@Query`: no hace falta tocar el JPQL.
- **Hooks sobreescritos**: si el proyecto sobreescribe `hookUuidFindDatabase`, `hookSaveGetExistRegister` o `hookDeleteFindByUuid`, la firma ahora devuelve `Optional<T>`. Un `return null` pasa a ser `return Optional.empty()`.
- **Tests con Mockito**: un `thenReturn(entidad)` sobre un método que ahora devuelve `Optional` pasa a `thenReturn(Optional.of(entidad))`. Los stubs que devolvían `null` para simular "no existe" se pueden borrar: Mockito ya devuelve `Optional.empty()` por defecto en un método que devuelve `Optional`.
