# Core 3.3.2

## Resumen

Un request con un archivo que supera el límite de multipart responde `413` con el formato de error de la API
(`ErrorResponseDTO`) y el código `ARCHIVO_DEMASIADO_GRANDE`. Es un arreglo compatible: no cambia ningún endpoint, DTO
ni permiso.

## Cambios

### Manejador global (`core-kernel`)

`ManejadorDeExcepcionesDeApi` sobreescribe `handleMaxUploadSizeExceededException` de `ResponseEntityExceptionHandler`
y responde el código nuevo `CodigoDeErrorKernel.ARCHIVO_DEMASIADO_GRANDE` (`413`).

Hasta 3.3.1 la excepción la resolvía la clase base de Spring: respondía `413` con el cuerpo `ProblemDetail` de Spring
(detalle "Maximum upload size exceeded"), sin `codigo`, y el front no lo podía distinguir como el resto de los errores.

Se sobreescribe el método de la clase base en vez de declarar un `@ExceptionHandler(MaxUploadSizeExceededException.class)`:
desde Spring 6.1 la clase base ya mapea esa excepción, y un segundo handler para la misma excepción hace fallar el
arranque por ambigüedad.

## Qué tiene que hacer un proyecto

Nada. Si el front discriminaba el 413 por el cuerpo de Spring, pasa a discriminarlo por `codigo`.

## Pendiente

`CrypterService.guardarArchivo` solo recibe el archivo completo en base64: un archivo grande se carga entero en memoria
(bytes más su base64). Queda pendiente una variante por streaming (`InputStream`), que requiere verificar que la API
de Crypter acepte el envío en streaming.
