# Core 3.4.0

## Resumen

El JWT propio (`core-protocolo-jwt`) y Malvinas (`core-protocolo-sso`) pueden estar habilitados a la vez en
`auth.protocolos`: cada estrategia reconoce su Bearer por el `alg` de la cabecera y deja pasar el ajeno sin error.
Suma el puerto `PoliticaDeAccesoExterno` (`core-identity`), que Malvinas consulta antes de crear o guardar el
usuario, y `renovarToken` deja de renovar el token de un usuario dado de baja. Es minor porque agrega un puerto.

## Cambios

### Convivencia de estrategias Bearer (`core-protocolo-jwt`, `core-protocolo-sso`)

- `AuthJwtService.getUsuario` y `getUsuarioDelToken` leen la cabecera del token sin verificarla. Si el `alg` no es
  `HS256` (o la cabecera es ilegible) responden `null`: no es su token. Con `HS256`, una firma inválida o un token
  vencido siguen lanzando `TOKEN_INVALIDO` / `TOKEN_VENCIDO`. `getUsuarioDelToken` con un token vacío sigue
  lanzando `TOKEN_REQUERIDO`.
- `AuthMalvinasService.getUsuario` responde `null` si el `alg` no es `ES256` (el único que acepta
  `MalvinasJwtDecoderConfig`), antes de decodificar el token.

Hasta 3.3.2 la primera estrategia de `auth.protocolos` que recibía el token de la otra lanzaba error
(`TOKEN_INVALIDO` o `SSO_AUTENTICACION_FALLIDA`) y la segunda nunca llegaba a resolverlo. `AuthService` no cambia:
el orden de las estrategias deja de importar porque cada una solo responde por su token.

### Puerto `PoliticaDeAccesoExterno` (`core-identity`)

```java
void validar(String protocolo, String identificador, UsuarioBase usuarioVigente)
```

`AuthMalvinasService` lo llama con `"malvinas"`, el legajo y el usuario vigente de ese legajo (`null` si todavía no
existe), después de buscarlo y antes de crearlo o guardarle los datos del token. Si lanza `ExcepcionDeApi`, el
error sale tal cual, sin envolverse en `SSO_AUTENTICACION_FALLIDA`, y no se crea ni se modifica ninguna fila.

La implementación por defecto (`IdentityConfiguracion`, `@ConditionalOnMissingBean`) no valida nada.

### `renovarToken` (`core-protocolo-jwt`)

`AuthJwtService.renovarToken` carga el usuario del refresh token filtrando `status = 0`. Un usuario dado de baja, o
inexistente, responde `REFRESH_TOKEN_INVALIDO`. Hasta 3.3.2 un usuario dado de baja podía seguir renovando su
sesión, y uno inexistente respondía `REGISTRO_NO_ENCONTRADO`.

Se actualiza el `@Descripcion` de `REFRESH_TOKEN_INVALIDO`, `TOKEN_INVALIDO` y `SSO_AUTENTICACION_FALLIDA` para
reflejar estos casos en el catálogo de errores del contrato (`docs/api`).

## Qué tiene que hacer un proyecto

- Nada para mantener el comportamiento: la política por defecto deja entrar a toda identidad de Malvinas.
- Para restringir el acceso por Malvinas, publicar un bean propio de `PoliticaDeAccesoExterno` que lance
  `ExcepcionDeApi` con un código del proyecto.
- Cambio visible: un Bearer cuyo `alg` no es `HS256` ni `ES256` (o con una cabecera ilegible) ya no responde
  `TOKEN_INVALIDO` / `SSO_AUTENTICACION_FALLIDA`. Ninguna estrategia lo reconoce y responde `401 NO_AUTENTICADO`.
